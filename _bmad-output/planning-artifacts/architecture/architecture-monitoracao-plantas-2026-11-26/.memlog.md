- (constraint) [ADOPTED] Greenfield MVP is a responsive mobile-first web application; no native app, installable PWA, write-offline mode, IoT, automated photo diagnosis, ML, social/community/commerce, shared household inventory, push, SMS, or email. Cached synchronized Inventory and Agenda are read-only, show last sync, and are stale/blocked from representing current state after 30 days.
- (constraint) [ADOPTED] Domain/API contract: normalize and deduplicate by accepted canonical scientific name; retain per-field source provenance, original and normalized values, retrieval time, translation/review status, merge result, and conflicts. Keep secrets server-side. Sources include Perenual, Trefle, Flora e Funga do Brasil, Embrapa AgroAPI, INMET/Open-Meteo.
- (constraint) [ADOPTED] Guest users can search the pre-purchase catalog and simulate care fit without authentication; saving a Plant to the synchronized Inventory requires an account.
- (constraint) [ADOPTED] Launch pilot is Taboão da Serra, SP, for reviewed indoor ornamentals, urban edible crops/herbs, and bonsai; unsupported profiles may be stored in inventory but cannot produce species-specific deterministic claims.
- (constraint) [ADOPTED] Local deterministic agronomic rules and fail-safe safety gates are sovereign. External sources only enrich asynchronously, never override care, toxicity, dosages, waiting periods, or safety; ambiguous/unreviewed profiles remain não resolvido/não suportado and unknown toxicity is N/A with precaution.
- (constraint) [ADOPTED] Agenda is deterministic, explains safe windows, accepts climate changes only after explicit user consent within Safe Window, falls back to deterministic rules on stale climate, batches only compatible tasks, and keeps critical safety tasks non-deferrable. MVP notifications stay in Agenda.
- (constraint) [ADOPTED] PRD owns product behavior and FRs; UX EXPERIENCE.md owns interaction/IA, DESIGN.md owns visual behavior. Account-backed inventory supports human-readable export and confirmed definitive deletion of active data, while communicating backup purge and legal retention.
- (direction) Coaching path selected; architecture is for implementation convergence by @sm/@dev and team alignment. Architecture docs are authored in English; user-facing domain terms, UI states, and messages remain Portuguese.
- (decision) [ADOPTED] Use a normalized relational PostgreSQL core: canonical species and reviewed profiles distinct from account-owned user plants; field-level provenance and conflict audit; user-owned cultivation locations; care tasks with rule identity/version and Safe Window; batches with task membership; append-only care events for completed/skipped/postponed/dismissed or schedule changes. Limit JSONB to raw external payloads and genuinely variable context. Preserve PostgreSQL-standard migrations and keep agronomic rules portable.
- (question) Cost constraints: compare managed Supabase free/low tiers against self-hosting; document quotas, pauses, backup/operational limits, and migration portability before binding deployment and worker topology.
- (constraint) [ADOPTED] Cost controls: persist normalized external fields and minimal field-level provenance, not full raw provider payloads; store species imagery and user photo attachments in Cloudflare R2, with private access/deletion controls for user photos. R2 currently has no egress fee and a bounded free allowance; operation/storage costs still apply beyond included usage.
- (constraint) [ADOPTED] Serverless app and worker paths must not open unpooled direct PostgreSQL connections. Prefer Supabase Data API/RPC over HTTPS with RLS; if a Worker uses PostgreSQL wire protocol, use Cloudflare Hyperdrive or Supavisor transaction pooling. Use direct connections only for suitable persistent/native migration operations.
- (question) Supabase Free can be paused after seven days of low activity, has bounded DB/egress quotas, and no downloadable backups; a real daily climate job may generate activity but does not guarantee availability. Public production availability and backups require a paid plan or explicit self-hosted operations; do not rely on synthetic keepalive as an availability design.
- (decision) [ADOPTED] Deploy a static Next.js export to Cloudflare Pages and use one Cloudflare Worker in TypeScript for HTTP API and scheduled jobs, with Supabase-managed PostgreSQL/Auth and Cloudflare R2 for media. Keep the application portable on PostgreSQL-standard migrations and isolate all provider secrets server-side.
- (decision) [ADOPTED] Worker fetch routes forward the caller's Supabase JWT to HTTPS Data API/RPC so PostgreSQL RLS scopes user data. The service_role secret is unavailable to ordinary user operations and is used only by trusted scheduled ingestion/climate handlers and an authenticated, confirmed account-deletion flow.
- (decision) [ADOPTED] Worker jobs use Postgres-owned job/run records with atomic lease acquisition using locked_until, cursor checkpoints, idempotency keys, bounded batches, retries/backoff, and visible failure status; no separate Redis or always-on worker. Public guest catalog responses may use edge caching; never cache personalized responses.
- (assumption) Cloudflare R2 and Postgres cannot participate in one atomic transaction. Account deletion is an idempotent saga: mark deletion pending and block writes, delete owner-scoped R2 objects in retryable batches, then delete the Auth user and cascade active Postgres data; report pending/completed state and disclose backup retention. Scheduled Cloudflare activity may reduce Free-plan inactivity risk but does not guarantee availability; production must trigger paid plan or explicit self-hosted SLO/backup ownership. Keep Worker Free CPU work tiny and batch/cursor; upgrade to Workers Paid if measured CPU needs exceed its Free limit.
- (assumption) The one-worker topology is accepted by the user. To minimize serverless Postgres connection pressure, use Supabase HTTPS Data API/RPC; use Hyperdrive or Supavisor transaction pooling only for code that needs PostgreSQL wire protocol. Migration and backup commands may use appropriate direct connections.
- (decision) [ADOPTED; supersedes the earlier one-Worker deployment decision] Deploy two Cloudflare Workers from one TypeScript repository: api-worker has only the public Supabase key and forwards a validated user JWT for RLS-scoped API access; cron-worker alone holds SUPABASE_SERVICE_ROLE_KEY and administrative R2 access for scheduled integrations, orphan cleanup, and confirmed deletion jobs. Keep admin endpoints internal and narrowly allowlisted.
- (decision) [ADOPTED] Authenticate inventory and sync accounts with Supabase Auth email plus password and mandatory email confirmation. Passwordless OTP/magic link is not a routine sign-in; use a single-use recovery link/OTP only for password recovery. Auth delivery is transactional only, not a care reminder channel; configure custom SMTP before public launch.
- (decision) [ADOPTED] User-photo limit: WebP, max 1200px and 2 MiB per file; max 5 per plant and 50 per account (100 MiB worst case); max 10 upload attempts per account per hour. Allow delete/replace when full. api-worker validates server-side size, declared type, and RIFF/WEBP signature; enforce quotas atomically in Postgres before object write.
- (decision) [ADOPTED] Photo storage uses deterministic owner-scoped object keys. Upload is a compensating workflow: reserve quota and pending media row, validate and store via an internal cron-worker R2 operation, finalize the Postgres reference, and immediately delete/release on failure; a weekly idempotent reconciliation removes stale unreferenced objects. Cross-service R2/Postgres deletion is not described as atomic.
- (decision) [ADOPTED] Catalog enrichment is a finite, budgeted queue: seed the reviewed baseline separately; enqueue only explicit unresolved user-requested species or approved small batches, process per-provider quotas in bounded increments, and stop automatically when empty or budget-exhausted. External candidates never resolve identity or publish rules without review.
- (constraint) [ADOPTED] Supabase Free is for development/staging only. Upgrade to Pro before opening production to real users to avoid inactivity pausing and obtain daily backups; daily Cloudflare Cron traffic does not replace the availability/backup commitment.
- (decision) [ADOPTED] Executable Layer A rules live in a typed, versioned TypeScript domain package in the repository, derived and reviewed from the local domain documents and covered by deterministic tests. PostgreSQL stores reviewed species profiles, confidence/support state, and provenance; external enrichment cannot edit rule code or authoritative fields.
- (decision) [ADOPTED] api-worker validates authenticated upload owner, quotas, content length and RIFF/WEBP signature, then invokes a private cron-worker through a Cloudflare Service Binding for R2 writes/deletes. cron-worker has no public route and is the only Worker with R2 administrative binding and Supabase service role; internal operations use narrow typed RPC methods and owner-scoped object keys.
- (constraint) [ADOPTED] Image cap is 5 per plant, 50 per account, 2 MiB each, 1200 px, WebP; limit upload attempts to 10/account/hour. When full, user can delete an older photo or replace the cover. Revisit these limits after the pilot based on real storage and usage.
- (decision) [ADOPTED] A climate snapshot is usable only while now is earlier than expires_at, where expires_at is the earlier of collected_at plus 24 hours and any provider-specified valid_until. Persist observed_at, collected_at, and expires_at; once expired, ignore climate suggestions and use the deterministic schedule.

- (decision) [ADOPTED after reviewer gate] Enforce owner-scoped composite relationships, immutable owner_user_id, and RLS USING/WITH CHECK; system job/tombstone records are service-only and not user-owned. Canonical taxon keys use one shared versioned normalizer (accepted genus+species, Unicode NFC, lowercase, normalized whitespace, no authorship), with synonyms retained as aliases.
- (decision) [ADOPTED after reviewer gate] Canonical CareTask status is pending/completed/dismissed; postpone keeps pending and changes proposed window. Only pending non-critical tasks may be dismissed; completed/dismissed are terminal except correction events. Safe Windows use half-open [start,end) in the user's IANA zone; ambiguous/nonexistent local times do not move tasks. Every task/batch mutation uses owner-scoped request idempotency and transactional projection/event writes; generated-task events carry rule/revision/package/projection provenance.
- (decision) [ADOPTED after reviewer gate] Task occurrence identity is owner+Plant+stable rule ID+normalized occurrence window; immutable rule revision and exact package version are stored separately. Rule changes require a reviewed pending-task migration plan and never rewrite completed history. Worker jobs use monotonic fencing tokens compared on every progress/result write.
- (decision) [ADOPTED after reviewer gate] packages/contracts is the versioned runtime-validated contract for API, Service Binding, RPC, and error schemas. Every error states code, retryability, retry-after when known, and commit state; retries reuse idempotency keys. Internal media methods accept validated bytes with reservation ID/request key; Cron resolves owner/object key from pending reservation and never accepts arbitrary keys.
- (decision) [ADOPTED after reviewer gate] Account deletion keeps a service-only opaque deletion tombstone without Auth FK or direct identifiers after completion. Cron idempotently verifies R2/active-row cleanup and Auth deletion, then marks terminal completion; an already-absent Auth user is accepted only after cleanup verification.
